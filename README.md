# FamilyCloud

FamilyCloud — домашнее облако для хранения и просмотра семейных фотографий. Проект ориентирован на самостоятельное размещение (self-hosted) и в дальнейшем — на удобное использование с телефона членами семьи.

> **Статус:** проект в разработке. Этот README фиксирует текущую архитектуру и порядок развёртывания. Перед установкой на постоянный сервер проверьте раздел «Что ещё нужно сделать».

## Возможности и планы

**Уже реализовано или разрабатывается:**
- ASP.NET Core API для работы с фотографиями;
- хранение метаданных в PostgreSQL;
- обработка фоновых задач через RabbitMQ (в том числе создание миниатюр);
- Outbox для надёжной публикации событий после сохранения данных;
- пользователи, персоны, роли и первоначальное создание администратора;
- приглашения пользователей (поток регистрации по приглашению ещё нужно проверить целиком).

**В планах:** мобильный клиент, полноценная авторизация, управление доступом, удаление фотографий, резервное копирование, мониторинг, удобное развёртывание для родственников.

## Технологии

- C# / .NET 10, ASP.NET Core;
- Entity Framework Core, PostgreSQL 17;
- RabbitMQ;
- Docker и Docker Compose;
- отдельный Worker для фоновых задач;
- Linux / Debian в качестве целевого сервера.

## Развёртывание на Debian

### 1. Подготовить сервер

Установить Docker Engine и Docker Compose Plugin. Проверить:

```bash
docker --version
docker compose version
```

Также понадобятся Git, доступ к репозиторию и место для фотографий, базы данных и резервных копий.

### 2. Получить проект

Клонировать репозиторий и перейти в его корень (туда, где находится `compose.yaml` или `docker-compose.yml`).

```bash
git clone <URL_РЕПОЗИТОРИЯ>
cd family-cloud
```

Адрес репозитория нужно вписать после публикации.

### 3. Настроить переменные окружения

Создать `.env` в корне проекта и задать значения, которые используются текущим Compose-файлом. Для PostgreSQL это, в частности:

```dotenv
POSTGRES_DB=familycloud_test
POSTGRES_USER=boris
POSTGRES_PASSWORD=<СИЛЬНЫЙ_УНИКАЛЬНЫЙ_ПАРОЛЬ>
```

Это **пример имён переменных**, а не готовый файл для копирования: свериться с актуальным `compose.yaml`, проверить настройки RabbitMQ, подключения API/Worker и пути хранения фотографий. Для постоянного сервера выбрать собственные логины и пароли.

**Безопасность:** не добавлять `.env` в Git; ограничить доступ к нему. Не передавать секреты в команды, которые сохраняются в истории shell. Учитывать, что переменные окружения контейнера могут быть доступны через Docker-инструменты; для более строгой защиты рассмотреть Docker secrets.

### 4. Проверить постоянное хранение данных

Перед запуском убедиться, что PostgreSQL и фотографии используют Docker volumes или bind mounts, а не только файловую систему временного контейнера.

Особенно важно при переносе на Debian:
- определить каталог хранения оригиналов и миниатюр;
- проверить права доступа к нему;
- убедиться, что пересоздание контейнеров не удаляет фотографии и базу;
- запланировать резервное копирование **и базы, и файлов**.

### 5. Запустить инфраструктуру

Из корня репозитория:

```bash
docker compose up -d postgres rabbitmq
```

Команда предполагает, что сервисы действительно называются `postgres` и `rabbitmq` в текущем Compose-файле. Проверить их готовность:

```bash
docker compose ps
```

### 6. Применить миграции базы данных

**Обязательный шаг до Bootstrap:** создать таблицы в новой базе с помощью миграций EF Core.

### 7. Создать первого администратора — Bootstrap

**ВАЖНО: на новой пустой базе выполнить один раз после миграций.**

```bash
docker compose run --build --rm bootstrap
```

Утилита запросит логин и пароль в интерактивном терминале. Ввод пароля скрыт.

Что делает Bootstrap:
1. Открывает транзакцию и получает транзакционную блокировку PostgreSQL.
2. Проверяет, существует ли администратор.
3. Если администратора нет — создаёт `Person` и связанного `User` с ролью `Administrator`.
4. Сохраняет обе записи и завершает транзакцию.
5. Если администратор уже существует — не создаёт второго.

Ожидаемые сообщения:

```text
Administrator created successfully.
```

или

```text
Administrator already exists.
```

**Не включать `bootstrap` в обычный автоматический запуск сервисов.** Это ручная одноразовая операция. В Compose для него используется профиль `tools`; запуск через `docker compose run` позволяет выполнить его по запросу.

При повторном развёртывании **с сохранённой базой** заново создавать администратора не требуется. Если база восстановлена из резервной копии, сначала проверить наличие администратора.

### 8. Запустить приложение

```bash
docker compose up -d --build
```

Убедиться, что API и Worker работают:

```bash
docker compose ps
docker compose logs --tail=100 api
docker compose logs --tail=100 worker
```

Имена `api` и `worker` сверить с текущим Compose-файлом. Если сервисы ещё не включены в Compose или требуют дополнительной настройки, завершить её перед запуском.

### 9. Проверить после запуска

- API доступен по ожидаемому адресу и порту.
- PostgreSQL и RabbitMQ готовы к работе.
- Таблицы созданы миграциями.
- Администратор существует; пароль в базе хранится **только в виде хеша**.
- Загруженная фотография сохраняется и доступна для просмотра.
- Фоновая обработка создаёт миниатюру.
- После перезапуска контейнеров фотографии и метаданные остаются на месте.

## Полезные команды

```bash
# Состояние контейнеров
docker compose ps

# Логи всех сервисов
docker compose logs -f

# Пересобрать и запустить сервисы
docker compose up -d --build

# Остановить сервисы, сохранив volumes
docker compose down

# Ручной запуск Bootstrap
docker compose run --build --rm bootstrap
```

**Осторожно:** `docker compose down -v` удаляет управляемые Compose volumes и может уничтожить данные PostgreSQL. Не выполнять без проверенной резервной копии.

## Резервное копирование и перенос

Для переноса с одной машины на другую недостаточно скопировать только исходный код. Нужно сохранить:

1. Дамп PostgreSQL (пользователи, метаданные фотографий, приглашения и др.).
2. Оригиналы фотографий и миниатюры (либо возможность безопасно пересоздать миниатюры).
3. Актуальный Compose-файл и необходимые настройки окружения — отдельно от Git и с соблюдением безопасности.
4. Сведения о путях хранения, домене, HTTPS и внешних портах.

После восстановления базы и файлов проверить согласованность записей с фотографиями. Bootstrap повторно не нужен, если администратор уже есть в восстановленной базе.

## Безопасность перед доступом из интернета

- Настроить HTTPS и reverse proxy (например, Nginx).
- Завершить и протестировать авторизацию и разграничение прав.
- Не публиковать наружу порты PostgreSQL и RabbitMQ без необходимости.
- Использовать отдельные надёжные пароли и не коммитить секреты.
- Продумать обновления, журналирование и восстановление после сбоя.
